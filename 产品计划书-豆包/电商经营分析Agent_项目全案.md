# 电商经营分析 Agent · 项目全案文档

> 复合型数据智能简历项目（数据分析 + 数据工程）· 目标：大厂数据智能方向
> 版本 V1.0 · 2026-09

---

## 一、项目概述

### 1.1 项目定位

**数据分析 Agent（领域无关）**：业务人员用自然语言提问，Agent 自动完成"取数 → 校验 → 归因 → 报告"全链路，输出带可追溯依据的归因结论与业务建议。**Agent 内核与行业知识解耦**——通过可插拔"领域包"机制落地电商（首个场景）、教育等多元行业。

- **上层**：多智能体分析链路（规划、SQL 生成、沙箱校验、归因、报告）——领域无关，一次构建全局复用
- **中层**：可插拔领域包（数据集 + 语义层指标 + 口径规则 + few-shot 样例 + 评测集，按 domain 组织）
- **下层**：dbt + DuckDB 分层数仓（ODS → DWD → ADS）+ 语义层（指标字典、维度定义、业务规则）

### 1.2 项目目标

1. 产出可落地、可演示、可量化的简历项目（8 周三阶段）
2. 深入电商业务逻辑（GMV、转化率、复购率口径建模与归因设计）
3. 通过"内核 × 领域包"架构证明可扩展性（电商跑通后，新增教育领域仅加配置不改代码）
4. 支撑大厂数据智能方向求职（同时覆盖数据智能 / AI 应用 / 数据开发三类岗位考察点）

### 1.3 背景与价值

- 2026-2027 大厂 AI 岗位密集开放：阿里 16 个业务集团同步招聘、AI 岗占比约 80%；字节首设 AI Agent 开发岗；腾讯、美团同步上线 Agent 开发岗，要求点名 Agent、Skills、MCP、RAG 等能力
- 数据岗位两极分化：取数型分析师内卷（需供比约 1.89），低端岗被 AI 替代；AI 数据工程师需求 +70%；"懂业务 + 懂数据 + 懂 AI"复合型人才稀缺
- 数据分析 Agent 是企业级刚需：阿里 DataWorks 多智能体问数（6 万+用户）、腾讯 NL2SQL 沙箱实践、蚂蚁 BIRD SOTA（81.67%）、行业案例准确率 58%→96%

## 二、产品形态与设计

### 2.1 输入与输出

**输入 ≠ 对话框**，本质是"业务意图"，4 件套：

| # | 输入 | 说明 |
|---|---|---|
| ① | 自然语言问题 | 对话框可见部分 |
| ② | 约束条件 | 时间范围/地区/指标（对话带出或页面筛选） |
| ③ | 对话上下文 | 多轮追问的基础 |
| ④ | 用户身份与权限 | 决定可访问的数据范围 |

**输出 ≠ 一段话**，本质是"分析报告对象"，5 件套：

| # | 输出 | 说明 |
|---|---|---|
| ① | 结论 | 自然语言归因结论 + 置信度 |
| ② | 证据 | 生成 SQL + 口径 + 数据来源（可追溯） |
| ③ | 图表 | 趋势/贡献拆解/对比 |
| ④ | 建议 | 下一步行动建议 |
| ⑤ | 追问 | "要不要下钻到单品"等引导 |

**内部各层输入输出形态**（越往下越结构化）：

| 层 | 输入 | 输出 |
|---|---|---|
| L1 交互层 | 对话框文本 + 会话ID + 身份 | 渲染页面（结论+图+SQL） |
| L2 编排层 | 结构化任务单（intent + sub_tasks） | 中间状态 |
| L3 能力层 | 口径查询 / SQL 执行请求 | 数据结果集 |
| L4 模型层 | Prompt（问题+知识+历史） | JSON / 工具调用请求 |

### 2.2 UI 设计

**三态切换**：首屏=引导态（教你怎么用）→ 对话态（一问一答）→ 结果态（报告卡）

**四个设计原则**：
1. 首屏引导：示例问题 chips + 指标拼问题区 + 欢迎语（零基础也能开始）
2. 结果结构化：每轮答案是"结论 → 图表 → 归因细节 → 建议 → 追溯 → 追问"报告卡
3. 渐进披露：SQL 与口径默认折叠，点击展开（信任感来自"能看到"，体验来自"默认不看"）
4. 引导常驻：输入框 + 追问 chips（"下钻到单品""换个维度"）

**页面布局**：顶栏（数据集选择器 + 评测/成本状态）· 左栏（会话历史/数据集管理/指标口径/**个人配置**/评测中心/数据血缘）· 主区（引导→对话→报告卡）· 底部常驻输入框

### 2.3 可视化与交互

**可视化三层**：
| 层 | 位置 | 内容 |
|---|---|---|
| ① 数据工程层 | D3/D6 | 质量报告：空值率条形图、字段分布直方图、血缘 DAG |
| ② 过程层 | Q3-Q8 | 链路状态动画、数据预览、SQL/口径展开（建立信任） |
| ③ 结果层 | Q11 | 分析结论图表（图必须匹配问题，非装饰） |

**交互四级**：
| 级 | 行为 |
|---|---|
| L1 对话交互 | 提问 → 追问 chips → 新一轮分析 |
| L2 图表交互 | hover 数值 · 点击柱/扇区下钻 · 图例切换 · 图表联动 |
| L3 参数交互 | 口径开关（含退款/净GMV）· 时间粒度（周/月/季）· 环比/同比 |
| L4 追溯交互 | 展开 SQL · 查看口径 · 查看血缘 |

**图表选型（图表必须匹配问题）**：

| 问题 | 图表 | 原因 |
|---|---|---|
| GMV 趋势 | 折线图 | 连续变化 + 环比标注 |
| 渠道贡献拆解 | 瀑布图/堆叠柱 | 表达"每项对总降幅的贡献" |
| 排名对比 | 柱状图 | 谁强谁弱 |
| 占比结构 | 环形图 | 部分-整体 |
| 转化漏斗 | 漏斗图 | 各环节流失 |
| 用户价值分布 | 直方图/箱线图 | 分布特征 |

**下钻闭环（核心交互）**：结论 → 点击图表元素 → 触发新一轮 Agent 调用（Q2-Q11）→ 新结论 → 继续下钻。图表是入口，Agent 是引擎。

### 2.4 数据源设计

**三层数据**：
| 层 | 内容 | 来源 | 网络搜索 |
|---|---|---|---|
| ① 核心事实层 | 订单/用户/商品/行为 | 用户提供数据集 / 企业数仓 | ❌ 搜不到 |
| ② 知识层 | 口径/规则/字段说明 | 企业内部文档 → 语义层/RAG | ❌ 内部知识 |
| ③ 外部情报层 | 行业趋势/竞品 | 网络搜索（可选） | ✅ 仅此层 |

**结论**：主线是"用户提供数据集"（或企业数仓）；网络搜索是可选的外部情报补充，不是主线，避免项目失焦。

**演进路径**：W1-W6 上传 CSV → DuckDB 数仓；W7-W8 数据接入层（CSV/MySQL/DuckDB 统一接口）；可选扩展 web_search 工具。

## 三、完整架构

### 3.1 认知框架

- **Agent 定义**：由大模型驱动的自主闭环——理解目标 → 拆解任务 → 调用工具 → 观察结果 → 决定下一步 → 直到完成。核心是循环不是直线。
- **四件套**：LLM（大脑）+ Tools（手）+ Memory（笔记本）+ Planning（工作手册），框架（LangGraph）是组装它们的舞台。
- **ReAct 循环**：想（Reason）→ 做（Act）→ 看（Observe）→ 循环 → 终止条件满足 → 输出。
- **工作流 vs Agent**：路径确定用工作流，需要灵活性用 Agent；生产系统 = "宏观工作流 + 微观 Agent"混合。

### 3.2 五层架构 + 四横切

| 层 | 管什么 | 关键组件 | 对应项目 |
|---|---|---|---|
| L1 交互层 | 用户入口、鉴权、会话 | 前端、FastAPI | frontend/ + backend/ |
| L2 编排层 | 流程：节点/边/重试/分支 | LangGraph 状态机 | agent/graph.py + nodes/ |
| L3 能力层 | 手与知识 | 工具、RAG、记忆、语义层 | sandbox.py + semantic/ |
| L4 模型层 | 谁来"想" | LLM API、模型路由 | 配置 |
| L5 基础设施层 | 数据底座、部署 | 数仓、Docker | warehouse/ |

**四横切**：安全沙箱 / 评测 CI / 可观测 trace / 成本控制

### 3.3 完整端到端流程（21 步）

**离线 · 数据工程（D1-D9，构建一次）**：

| 步骤 | 做什么 | 关键产出 | 对应项目 |
|---|---|---|---|
| D1 数据接入 | 上传 CSV/连库（HTTPS+JWT+租户隔离） | 通过校验的原始数据 | backend/ 上传接口 |
| D2 存储登记 | 原始文件不可变存储 + datasets 元数据表 | datasets 表 | data/ 目录 |
| D3 数据探查 | 空值/重复/异常/主键扫描 | 数据质量报告 | quality_report.py |
| D4 建模分层 | ODS→DWD 明细宽表→ADS 指标宽表（星型） | 三层数仓 | warehouse/models/ |
| D5 开发加工 | dbt 模型，幂等可重建 | 可版本管理的模型 | dbt 项目 |
| D6 质量测试 | 主键唯一/金额非负/行数波动告警 | 质量门 | dbt tests |
| D7 语义层 | 指标字典：口径+表达式+过滤规则 | 口径唯一来源 | semantic/ |
| D8 调度时效 | T+1 刷新，ADS 带 data_date | 时效标注机制 | 调度脚本 |
| D9 血缘元数据 | 指标→SQL→源表→数据集依赖链 | lineage 表 | lineage.py |

**在线 · 问答分析（Q1-Q12，每次请求）**：

| 步骤 | 做什么 | 关键设计 |
|---|---|---|
| Q1 输入 | 三种入口（对话框/示例/指标拼装）+ 身份权限 | UI 引导态 |
| Q2 澄清 | 意图/口径不明 → 反问确认 | 澄清分支 |
| Q3 规划 | 拆解 intent + sub_tasks（先确认事实再拆原因） | 规划节点 |
| Q4 上下文组装 | 口径 + Schema + 历史 + RAG → 一条 Prompt | 知识注入 |
| Q5 SQL 生成 | 受约束生成（schema 白名单 + 口径 + few-shot） | SQL 节点 |
| Q6 安全执行 | 只读沙箱 + 行级权限代码强制 + LIMIT + 超时 | sandbox.py |
| Q7 校验 | 语法（EXPLAIN）+ 口径（模型自检）→ 失败重写 | 校验节点 |
| Q8 质量确认 | 结果空值/异常波动检查 | 质量门 |
| Q9 分析归因 | 指标计算 + 环比同比 + 维度拆解 + 贡献度 + 显著性 | 归因节点 |
| Q10 结论 | 根因/贡献/置信度 + 假设标注 + 时效标注 | 结论组装 |
| Q11 报告 | 5 件套：结论/证据/图表/建议/追问 | 报告节点 |
| Q12 反馈闭环 | 渲染 → 追问循环 → qa_log 沉淀 → 评测集更新 | 闭环 |

**横切四件套**：安全（沙箱/权限/脱敏/审计）· 评测（qa_log→评测集→CI 回归）· 可观测（全链路 trace）· 成本（缓存/模型路由）

**闭环逻辑**：Q12 的 qa_log 回流 → ①评测集新增用例（防退化）②失败案例反改 D7 语义层 / Q5 few-shot（准确率螺旋上升）。离线数据工程是地基，在线分析是引擎，评测回流是油门。

### 3.4 领域扩展机制（内核 × 领域包）

**设计原则**：Agent 内核与行业知识完全解耦。

| 层 | 内容 | 是否随行业变化 |
|---|---|---|
| 内核 | 规划 / SQL 生成 / 沙箱 / 校验 / 归因（环比同比·贡献度·显著性）/ 报告 | ❌ 领域无关，写一次全局复用 |
| 领域包 | 数据集 + 语义层指标 + 口径规则 + few-shot 样例 + 评测集 | ✅ 按 domain 组织，可插拔 |

**新增一个领域的操作（三步，零内核改动）**：
1. 接入新数据集（datasets 表标注 domain）
2. 配置语义层（semantic_metric / semantic_rule 加 domain 字段）
3. 写评测用例（eval 目录按 domain 分：eval/ecommerce/、eval/edu/）

**数据工程按领域组织**：`warehouse/models/{ecommerce,edu}/` 分模型目录。

**面试分水岭**："行业知识是可插拔的领域包，新增行业只加配置不改代码——这是从 demo 到平台的区别。"

### 3.5 模型层：密钥架构与 BYOK（C 模式）

**核心原则**：API Key 只活在服务端，前端永不接触；"谁的 Key 都行，但 Key 必须只在服务端"。

| 模式 | 谁出 Key | 门槛 | 风险 | 适用 |
|---|---|---|---|---|
| A 平台统一 Key | 平台 | 低 | 用户滥用/刷额度 → 需限流配额 | 默认 |
| B BYOK 自带 Key | 用户 | 高 | 用户 Key 泄露 → 加密存储 | 自托管/高级用户 |
| **C 混合（本项目采用）** | 默认平台 + 高级用户绑定自有 | 中 | 需隔离计费 | 商业化最佳 |

**C 模式落地**：

| 层 | 实现 |
|---|---|
| users 表 | 增加 provider（default/bring_your_own）、enc_key（AES 加密，解密密钥在服务端）、key_status |
| 网关 | resolve_provider(user)：默认走平台 Key；高级用户走自有 Key |
| 成本隔离 | qa_log 增加 provider、cost 字段，按用户聚合 |
| 前端 | 设置面板"绑定我的 API Key（可选）"，明文只在本机表单，提交后后端加密存储 |
| 安全清单 | 前端零 Key · .env 不入 Git（.gitignore）· 日志脱敏 · 密钥上云 KMS（演进） |

**防泄露工程清单**：Key 只出现在服务端环境变量 / 密钥管理服务；Git 仓库排除 .env；请求日志打码；后端代理转发，前端只与自己的后端通信。

## 四、实体设计（18 张表 · 五组）

### 4.1 实体总览

| 分组 | 表名 | 层级 | 作用 |
|---|---|---|---|
| 维度表(4) | dim_user / dim_product / dim_category / dim_channel | ODS | 分析维度 |
| 事实表(3) | fact_order / fact_order_item / fact_user_behavior | ODS | 交易与行为事实 |
| 加工层(2) | dwd_order_detail / ads_trade_daily | DWD/ADS | 口径统一来源 / 毫秒查询 |
| 语义与评测层(5) | semantic_metric / semantic_dimension / semantic_rule / eval_case / qa_log | 独立 | 口径、规则、评测、可观测 |
| 个人配置层(4) | metric_category / metric_group / metric_group_item / user_config | 独立 | 分类树、指标组、用户偏好（见 4.7） |

### 4.2 维度表

| 表 | 粒度 | 关键字段 |
|---|---|---|
| dim_user | 每用户一行 | user_id(PK)、性别、年龄段、城市/省份、注册时间、渠道、会员等级、is_test |
| dim_product | 每 SKU 一行 | product_id(PK)、category_id(FK)、品牌、商品名、标准售价、上架时间、状态 |
| dim_category | 每类目一行（树形） | category_id(PK)、parent_id、类目名、level(1/2/3) |
| dim_channel | 每渠道一行 | channel_id(PK)、平台、店铺名、渠道类型（自营/第三方/直播）、地域 |

### 4.3 事实表

| 表 | 粒度 | 关键字段 | 要点 |
|---|---|---|---|
| fact_order | 每订单一行 | order_id、user_id、channel_id、下单/支付时间、状态、支付方式、配送方式、应付/优惠/运费/实付金额 | 状态是 GMV 口径"开关" |
| fact_order_item | 每订单内每商品一行 | order_item_id、order_id、product_id、数量、单价、小计、退款状态/金额 | 品类/单品分析入口 |
| fact_user_behavior | 每次行为一行（按天分区、采样） | behavior_id、user_id、product_id、行为类型(pv/加购/收藏/购买)、时间、来源页、渠道 | 转化漏斗来源 |

### 4.4 数仓加工层

| 表 | 层级 | 说明 |
|---|---|---|
| dwd_order_detail | DWD | 明细宽表：订单明细×订单×用户×商品×类目×渠道 join，含下单/支付/退款三组时间金额；指标计算唯一来源 |
| ads_trade_daily | ADS | 日×渠道×类目×城市：GMV、订单量、支付订单数、买家数、UV、转化率、客单价、退款金额、复购买家数 |

### 4.5 语义与评测层

| 表 | 关键字段 | 作用 |
|---|---|---|
| semantic_metric | metric_id、**domain**、指标名、口径说明、计算表达式、过滤规则、来源表、口径版本 | 解决"同一指标多口径"；domain 区分领域 |
| semantic_dimension | dimension_id、**domain**、维度名、字段映射路径、层级 | 维度统一映射 |
| semantic_rule | rule_id、**domain**、规则名（环比/同比/测试用户剔除）、描述、适用范围 | 写入 Prompt 与校验逻辑 |
| eval_case | case_id、**domain**、自然语言问题、期望指标/断言、难度、状态 | 评测闭环（按领域分目录） |
| qa_log | log_id、问题、SQL、结果、是否正确、token 成本、延迟、trace_id、模型、**provider** | 评测与成本数据来源（含 BYOK 计费） |

### 4.6 关键口径决策

| 口径项 | 定义 |
|---|---|
| GMV | 支付成功订单实付金额合计，剔除未支付/取消；含退款/净 GMV 用开关切换 |
| 转化率双口径 | A=支付买家/访问UV（行为日志）；B=支付订单/下单订单。禁止混用 |
| 复购率 | 周期内购买≥2次用户 / 购买用户（默认自然月） |
| 时间口径 | GMV 按支付时间（非下单时间） |
| 测试数据 | is_test=1 一律剔除 |

### 4.7 个人配置与分类体系（新增 4 张表）

将语义层能力暴露为左侧"个人配置"面板的用户可操作结构：

| 表 | 关键字段 | 作用 |
|---|---|---|
| metric_category | category_id、parent_id、name、level、domain、sort | **指标分类树**（文件夹）：静态归属，一个指标唯一挂载 |
| metric_group | group_id、owner_id、name、description、is_public | **指标组**（收藏夹）：用户把常用指标打包（如转化率+复购率→"健康度组"） |
| metric_group_item | group_id、metric_id、sort | 组-指标多对多关联（一个指标可在多个组） |
| user_config | user_id、active_domain、provider、key_status、output_pref、chart_pref、default_time_range | 个人配置（输出偏好/默认领域/密钥状态） |

**分类树与指标组的分工（关键区分）**：
- **分类树** = 指标的"归属"（文件夹）：由管理员/内置定义，层次结构（如 经营分析 → 流量/交易/用户），一个指标只挂一个分类
- **指标组** = 用户的"快捷打包"（收藏夹）：用户自建，可跨分类（如"转化率+复购率"打包为健康度组），一个指标可在多个组

**输出偏好（output_pref）三档**：汇总结论 / 结论+图表 / 完整报告（含 SQL 与血缘）
**自建资源包边界**：用户自建指标只允许"选字段 + 选聚合（sum/count/avg/rate）"，高级表达式走受控 DSL 校验——防止自建指标变成自由 SQL 绕过沙箱。

## 五、数据安全与存储设计

### 5.1 数据生命周期安全控制

| 环节 | 控制 | 落地 |
|---|---|---|
| ① 上传 | HTTPS + JWT 鉴权 + 格式/大小校验 | backend/ |
| ② 存储 | 按租户隔离目录 + 静态加密 + 原始文件不可变 | data/ |
| ③ 登记 | 元数据表记录归属/字段/权限规则/版本 | datasets 表 |
| ④ 入数仓 | ODS→DWD→ADS，敏感字段脱敏，dbt 可重建 | warehouse/ |
| ⑤ 查询 | 只读沙箱 + 行级权限强制过滤 + 审计日志 | sandbox.py + qa_log |

**核心原则**：安全不能靠提示词提醒，必须靠代码强制（行级权限在 SQL 生成后由程序拼 WHERE，不是依赖模型自觉）。

### 5.2 存储两阶段

**MVP**：
```
data/
└── tenant_1001/          ← 每用户一目录（隔离）
    └── raw/              ← 原始 CSV 只读不可变
```
元数据表：
```
datasets(dataset_id, owner_id, name, source_type,
         storage_path, schema_json, permission_rule,
         status, uploaded_at)
```

**企业级演进**：原始文件 → 对象存储（OSS/S3 加密）；结构化数据 → 数据库/数仓（MySQL/云数仓）；加工层 dbt 可重建。**原始层不可变、加工层可重建**。
